## PART I — STRATEGY (rewritten in light of research on technology-evaluation practice)

### 1. The Objective, reframed around how this audience actually evaluates

**The prior framing of this section stated SOVEREIGN's own priorities in order.** That's
necessary but insufficient — it answers "what do we think matters" without first answering
"what will the room actually be testing for." Both are needed; this version leads with the
second, since it changes how the first should be presented, not what it is.

**Researched, not assumed: a segment-scoped technology evaluator's first, most unforgiving
filter is outcome-orientation, not feature completeness.** A platform that can't state
plainly what real problem it solves, for whom, and how that's measured, reads as "shelfware
with a good demo" regardless of what was built. **SOVEREIGN's answer, stated once, plainly,
for use at the top of the demonstration:** PPBE execution governance with a deterministic —
not AI-judgment-based — compliance layer, and a real, now live-confirmed audit trail. Every
other demo beat exists to substantiate this claim, not to compete with it for attention.

**Demo-ready, precisely, updated:** the walkthrough half of the readiness bar — genuinely
met since v3.4 for the original scope — now includes the platform's single largest
historical gap, closed this week: Walkthrough H Parts 4 and 6, the exact sequence every
governance document this arc has named as the platform's oldest and most load-bearing
unverified claim, ran live and held completely. **What remains before the demonstration
itself is not platform work — it's rehearsal, framing, and honest preparation for the
specific questions this kind of evaluation reliably asks.** See Part XII.

**A real evaluation gate has more than two outcomes — Advance / Refine / Pause / Stop is the
researched structure, not a binary yes/no — and it's worth stating plainly what this plan is
actually aiming for.** Given the current state (9.6/10 readiness, zero MAJOR or BROKEN
findings across a genuinely comprehensive audit, the platform's oldest claim now
live-confirmed), **the realistic and stated target of this plan is Advance.** The honest
remaining gaps — a sidebar-content decision, two Walkthrough parts never run, a scoped but
not-yet-built backlog — are exactly the shape of thing a real evaluator expects to see named
precisely, not the shape that should read as reason for Pause. Part XII gives the specific
language for presenting them that way.

## PART XII — CTO EVALUATION LENS: THE PREP PLAYBOOK (new this version)

**What this is, and how it differs from the System Prompt's Section 5:** Section 5 sets
standing principles for how the Governance Agent should orient ongoing work as the
demonstration approaches. This is different — it's the concrete mapping from each
researched evaluation criterion to SOVEREIGN's specific, actual evidence, organized so it
can be used directly while preparing for or conducting the demonstration itself.

### The six criteria, each with SOVEREIGN's actual answer and where it lives in the demo

**1. Outcome-orientation — "what real problem, for whom, measured how."**
*SOVEREIGN's answer:* PPBE execution governance with a deterministic compliance layer and a
real audit trail, for the program managers, compliance officers, and analysts who currently
do this work without one. *Where it lives:* stated once, plainly, before any screen is
shown — not left for the platform to imply through feature demonstration alone.

**2. Real-condition reliability evidence, not demo polish.**
*SOVEREIGN's answer:* the fifty-one-screen comprehensive audit (zero MAJOR/BROKEN findings,
Sessions 66-68) and Walkthrough H Parts 4 and 6 — the platform's own oldest, most
load-bearing claim — run live in a real browser and confirmed holding, not just
code-verified. *Where it lives:* Demo Scope item 3 (Part I §2), presented as evidence with
its method stated, not asserted as a bare claim.

**3. Security/compliance boundary confirmation.**
*SOVEREIGN's answer:* GD-10 — this platform processes UNCLASSIFIED data only; an attempt to
process CUI, SECRET, or TOP_SECRET data is blocked and logged, not silently mishandled.
*Where it lives:* Demo Scope item 2 (Part I §2) — a stated, demonstrated beat, early, not a
footnote reached only if asked. **If time allows, this is worth an actual live
demonstration** (attempt a blocked classification, show the block and the log entry) rather
than a described claim — a shown boundary is stronger evidence than a described one.

**4. Realistic, tailored data as a credibility signal.**
*SOVEREIGN's answer:* real multi-year program lifecycles (Session 70) — one program closing
out, one beginning, three spanning the full FY2025-2028 window — with real narrative arcs,
not padded or generic figures. *Where it lives:* Demo Scope item 5 (Part I §2). **The
honest gap on this same dimension:** WH-13 — synthetic employee IDs instead of names in
SCRIBE's T&T queue — is real and worth a conscious decision about whether to address before
the demonstration or name plainly if asked, rather than let it surface as an unaddressed
surprise.

**5. Integration complexity, lock-in risk, and total cost of ownership.**
*SOVEREIGN's answer, ready if asked:* zero new production dependencies added across the
entire Session 62-70 arc, zero vulnerabilities, confirmed independently every session — real
evidence of low integration risk, not an assertion. On cost: the D4-6 (API key
architecture) and F2 (session-store extraction) deferrals are honest, reasoned answers to
"what would production actually require" — deliberately not yet built, with the reasoning
stated, which is a stronger position than an unexamined "it's ready" would be.
*Where it lives:* held in reserve for Q&A, not a scheduled beat — this is the kind of
question a real evaluator asks after the demonstration, not during it.

**6. The four-outcome gate, and what each outcome would actually mean here.**
- **Advance** — the stated target, and the realistic one given current readiness. Continued
  investment, a real path to the next phase.
- **Refine** — the honest fallback if the room lands here instead: the specific, named,
  bounded gaps (WH-26's tooltip content decision, the WH-15/16/23 backlog, Walkthrough Parts
  7-8) are exactly what "refine" would target — not a re-architecture, a punch list.
- **Pause** — worth naming plainly what this plan believes would have to be true for Pause to
  be the right call: a finding suggesting the platform's core reliability claims don't hold,
  which the Session 62-70 arc's own verification discipline was built specifically to catch
  and hasn't found.
- **Stop** — not argued against here; simply, nothing in this arc's evidence points toward it,
  and this plan doesn't pretend otherwise as false confidence.

### Three practical things this plan recommends doing before the room, not just knowing

**Tell the story, not the feature list.** Researched finding, consistent across every
practitioner source on what separates a convincing technical demonstration from an
unconvincing one: organize around "why should this specific audience care," not a
module-by-module tour. The Demo Scope order in Part I §2 is built for this — use it as a
narrative arc, not a checklist to read from.

**Test the actual presentation environment, not just the platform.** A repeatedly-named
credibility cost in practitioner research is environment mismatch on the day itself — a
different browser, a stale build, an untested network condition. This is logistics, not
platform readiness, and it's real: confirm the actual presentation setup — machine, browser,
network — matches what was rehearsed on, before the day, not the morning of.

**Decide, before walking in, exactly how to talk about what's honestly not done.** WH-26,
Walkthrough Parts 7-8, the WH-15/16/23 backlog, the D4-6/F2 deferrals — none of these are
weaknesses to manage around or hope don't come up. Named, bounded, reasoned gaps are what a
real technical evaluator expects and credits. This entire arc's development discipline —
honest disclosure banners, precise findings over vague claims, verified reliability over
asserted reliability — is itself the evidence that this is an organization worth continued
investment in. Say that directly if it's true, which the evidence in Parts I through IX of
this plan supports.
